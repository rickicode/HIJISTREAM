# Netflix-style Browse + 7-language i18n system (v2)

This change introduces a custom i18n system supporting 7 languages across the Expo mobile and React web apps, replaces the mobile 5-tab navigation with a Netflix-style 4-tab layout (Home, Browse, Downloads, Profile), adds Genre/Country grid navigation on both platforms, and makes all TMDB API calls language-aware through parameterized cache keys and URL query strings. The v1 issues (genre detail fetching wrong data, missing locale in query keys, untranslated strings) have all been addressed.

**Watch for:** The mobile `getDiscoverByGenre` passes a full locale code (e.g., `'en-US'`) through `getApiLanguageParam` which only maps short codes (`'en'`), causing non-Indonesian users to get `language=id-ID` in the explicit URL parameter (confirmed). All three new API methods (`getGenres`, `getDiscoverByGenre`, `getDiscoverByCountry`) embed `language=` in their endpoint URLs, but `fetchWithCache` unconditionally appends its own `language=` parameter too, producing duplicate query parameters in every request (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The i18n architecture is a lightweight React Context on both platforms with no heavy dependencies, sharing the same shape: `LanguageProvider` at the root, a `useTranslation()` hook, and 7 JSON locale files. Mobile adds device language detection via `expo-localization`.

The API layer has a language conflict: `fetchWithCache` was designed to be the single point where language gets appended to every URL, but the three new methods (`getGenres`, `getDiscoverByGenre`, `getDiscoverByCountry`) also embed language in their endpoint strings. This produces duplicate `language=` query parameters. On mobile specifically, `getDiscoverByGenre` passes a full locale code through a short-code lookup map, producing the wrong language for non-Indonesian users in the explicit parameter.

1. **Mobile `getDiscoverByGenre` produces wrong language for non-`id` users** — `getApiLocale()` returns full locale codes like `'en-US'`, but `getApiLanguageParam()` maps only short codes (`'en'`). Fix: pass the short `locale` code instead of `getApiLocale()`, or make `getApiLanguageParam` handle both formats.
2. **Duplicate `language=` query parameters on all new endpoints** — `getGenres`, `getDiscoverByGenre`, and `getDiscoverByCountry` embed `language=X` in their endpoint URLs. Then `fetchWithCache` unconditionally appends another `language=Y`. Every request to these endpoints sends two `language` params. Fix: either remove the explicit language from these endpoint strings (let `fetchWithCache` handle it), or make `fetchWithCache` skip appending when the URL already contains `language=`.
3. **`getGenres` cache key still doubles language** — The cache key is `genres_${type}_${language}`, then `fetchWithCache` prepends the language again, producing keys like `genres_movie_id-ID_id`. Not a correctness bug, but an asymmetry with other methods that could confuse maintenance.

## Duplicate language parameters in API URLs

`fetchWithCache` was designed as the centralized language injection point — it reads the current language, appends `language=` to every URL, and prefixes the language to every cache key. The pre-existing methods (`getPopularMovies`, `getTrendingMovies`, etc.) pass clean endpoints without language parameters, letting `fetchWithCache` handle it.

The three new methods break this contract by embedding language in their own endpoint strings:

```javascript
// getDiscoverByCountry
`/discover/${type}?with_origin_country=${countryCode}&language=${language}&page=${page}`

// getDiscoverByGenre
`/discover/${type}?with_genres=${genreId}&language=${apiLang}&page=${page}`

// getGenres
`/genres/${type}?language=${language}`
```

Then `fetchWithCache` appends another `language=...`:

```javascript
const separator = endpoint.includes('?') ? '&' : '?';
const url = `${BASE_URL}${endpoint}${separator}language=${langParam}`;
```

Result: `/discover/movie?with_genres=28&language=id-ID&page=1&language=id-ID`. Whether this causes incorrect behavior depends on which duplicate parameter the backend uses. The two values may disagree (see next section).

The fix: remove `language=` from the endpoint strings in all three new methods and let `fetchWithCache` handle it, matching the pattern of every other method.

## Mobile `getDiscoverByGenre` language mismatch

The mobile genre detail screen calls `getApiLocale()` which returns full BCP-47 locale codes (`'en-US'`, `'ja-JP'`, etc.) and passes that to `getDiscoverByGenre`:

```javascript
const language = getApiLocale(); // 'en-US'
api.getDiscoverByGenre('movie', id, language, pageParam)
```

Inside `getDiscoverByGenre`:
```javascript
const lang = language || await getCurrentLanguage(); // 'en-US'
const apiLang = getApiLanguageParam(lang); // localeMap['en-US'] → undefined → 'id-ID'
```

`getApiLanguageParam`'s map has keys `{id, en, es, pt, hi, ja, ko}` — short codes only. A full locale like `'en-US'` falls through to the default `'id-ID'`. So the explicit `language=` in the URL is always `'id-ID'` for non-Indonesian users.

The duplicate parameter from `fetchWithCache` will have the correct value (it reads `getCurrentLanguage()` which returns the short code). Whether the user sees correct content depends on which `language=` param the backend prioritizes.

The web version doesn't have this bug because its components pass the short `locale` code directly.
