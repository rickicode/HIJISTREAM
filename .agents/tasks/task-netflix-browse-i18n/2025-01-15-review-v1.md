# Netflix-style Browse + 7-language i18n system for mobile and web

This change replaces the mobile app's 5-tab bottom navigation (Home, Movies, TV, Anime, Search) with a Netflix-style 4-tab layout (Home, Browse, Downloads, Profile), adds a Browse screen with Genre/Country grid navigation to both platforms, and introduces a custom i18n system supporting 7 languages across the Expo mobile and Vite web apps. Language detection uses `expo-localization` on mobile and defaults to Indonesian (`id-ID`) on web, with all TMDB API calls now language-aware through parameterized cache keys and URL query strings.

**Watch for:** The genre detail screen on mobile passes `null` as the country code to `getDiscoverByCountry`, which means it fetches unfiltered discover results rather than genre-filtered content (confirmed). The web genre detail screen similarly ignores the genre ID entirely and fetches `getPopularMovies` instead (confirmed). The mobile home screen query keys don't include `locale`, meaning content won't refetch when the user changes language mid-session (confirmed).

## High-level view

The i18n system is a lightweight React Context that avoids heavy dependencies like i18next. Both platforms share the same architecture: a `LanguageProvider` wrapping the app root, a `useTranslation()` hook returning `t()`, `locale`, `setLocale`, and `getApiLocale()`, and 7 JSON locale files with identical key structures. Mobile adds `expo-localization` for device language detection on first launch.

The Browse screen replaces Search in the mobile tab bar and appears as an inline section on the web home page. Both use the same `GENRE_IDS` and `TMDB_COUNTRIES` constants from `api.js`, with tappable cards that navigate to detail screens. The detail screens use `useInfiniteQuery` for paginated loading, but the mobile genre detail fetches generic discover results rather than genre-specific content, making it a misleading navigation target.

The web `fetchWithCache` appends `language=` to every API call and prefixes the language to every cache key, so language switches correctly invalidate and refetch content. The mobile equivalent follows the same pattern. However, the mobile home screen's react-query keys omit `locale`, so react-query's in-memory cache will serve stale language content until the component remounts.

## Genre detail screens fetch wrong content

The genre detail screen is the most visible gap in this change. On mobile, `genre/[id].jsx` receives the TMDB genre ID from the route parameter but never uses it for filtering. The `queryFn` calls:

```javascript
api.getDiscoverByCountry('movie', null, language, pageParam)
```

This sends a request with `with_origin_country=null`, which either errors or returns unfiltered discover results. The user taps "Action" expecting action movies and gets a generic movie list.

On web, `GenreDetail.jsx` takes a different but equally wrong path — it calls `api.getPopularMovies(pageParam)` regardless of which genre card was clicked. The `id` param is used only for the header title lookup, not for data fetching.

Neither platform has a `getDiscoverByGenre(type, genreId, language, page)` method in their API utilities. The TMDB discover endpoint supports `with_genres=28` (for action), so the fix is adding that method and calling it with the route param.

## Mobile query keys don't trigger language refetch

The web home page includes `locale` in every react-query key:

```javascript
queryKey: ['trending-movies-home', locale],
```

The mobile home page omits it:

```javascript
queryKey: ['trending-movies-home'],
```

Since the mobile `fetchWithCache` includes language in the cache key, a cache miss will fetch the correct language. But react-query doesn't know the data is stale when language changes — it'll keep serving the previous response from its in-memory cache until the TTL expires or the component remounts. The user switches from Indonesian to Japanese, and the home screen content stays Indonesian until they pull-to-refresh or navigate away and back.

## Partial i18n coverage on mobile home

The mobile home screen builds rail titles with partial translation:

```javascript
title={`${t('common.trending')} Movies`}
title={`${t('common.trending')} TV`}
title={`${t('common.trending')} Anime`}
```

The web equivalent uses the correct pattern: `t('common.trending') + ' ' + t('nav.movies')`. The mobile version will display "Sedang Tren Movies" for Indonesian users — a visible half-translation that undermines the i18n effort.

## Doubled language in getGenres cache key

The `getGenres` method passes `language` as part of its own cache key (`genres_${type}_${language}`), and then `fetchWithCache` also prepends the language code. The resulting key is `genres_movie_id-ID_id` — doubled but not incorrect. This asymmetry with other methods (which don't embed language in their keys) could confuse maintenance. Consider removing the language from the `getGenres` key since `fetchWithCache` already handles isolation.

## Downloads subtitle not localized

`downloads.jsx` renders a hardcoded English string:

```jsx
<Text style={styles.subtitle}>Your downloads will appear here</Text>
```

This should be a translation key (e.g., a new `downloads.emptyState` key added to all 7 locale files).
