# Audit fixes: cache alignment, input validation, ID regex widening, and TMDB 404 handling

This change addresses findings from a code audit against the PRD plus a user-reported bug where clicking a movie or series after an APK update produced a 404. The audit fixes align client-side cache TTLs with the PRD specification (24h/7d/30d/1h), add server-side input validation for `page` and `query` parameters, harden the VideoPlayer origin allowlist, improve server cache eviction, and stabilize the Home page hero selection. The bug fix widens the ID-matching regex in all three API handlers (Bun server, Cloudflare Pages function, Vercel middleware) from `\d+` to `[\w]+`, so non-numeric IDs no longer 404 at the routing layer, and TMDB 404 responses now propagate as proper 404s to the client.

**Watch for:** The `[\w]+` regex opens the ID parameter to arbitrary strings including path-traversal-adjacent patterns (confirmed). Input validation was added to the Bun server but not to middleware.js or functions/api (confirmed). Server-side cache TTLs remain at 5min/10min, diverging from the client-side 24h/7d values just aligned to the PRD (confirmed).

## High-level view

The cache TTL alignment is client-only. The `CacheManager` in `apps/web/src/utils/cache.js` now holds list data for 24 hours and detail data for 7 days, matching the PRD, but the Bun server's in-memory TTLs (`TTL.LIST = 300000ms`, `TTL.DETAIL = 600000ms`) were not touched. The client cache will mask TMDB updates for far longer than the server would have served them fresh.

The ID regex change from `(\d+)` to `([\w]+)` solves the immediate 404 bug but `\w` includes `[A-Za-z0-9_]`, meaning any alphanumeric string passes routing and is forwarded directly into the TMDB API path via string interpolation with no length-bounding.

Input validation (page 1-1000, search query non-empty and max 200 chars) is implemented only on the Bun server. The Vercel middleware and Cloudflare Pages function — which serve the same API in their respective deployment targets — do not validate these parameters.

The cache eviction replacement sorts all 10,000 entries on every insert at capacity, introducing O(n log n) cost where the original FIFO was O(1).

## Server/client cache TTL mismatch

The client-side `cache.js` now declares `CONTENT_LIST: 86400` (24 hours) and `CONTENT_DETAIL: 604800` (7 days) in seconds, stored in localStorage. The Bun server's in-memory TTL constants remain unchanged:

```javascript
const TTL = {
  LIST: 300000,        // 5 minutes
  DETAIL: 600000,      // 10 minutes
  SEARCH: 120000,      // 2 minutes
};
```

User fetches data → server holds it for 5 minutes → client caches it for 24 hours. If TMDB removes a title or changes ratings within those 24 hours, the client serves stale data even though the server would have fetched fresh data long ago. The React Query `staleTime: 60000` doesn't help here because the `fetchWithCache` wrapper short-circuits before the network call when the localStorage entry is fresh.

## ID parameter widening and injection surface

All three API handlers now use `([\w]+)` for content IDs:

```javascript
else if (pathname.match(/^\/api\/movie\/([\w]+)$/)) {
  const match = pathname.match(/^\/api\/movie\/([\w]+)$/);
  const movieId = match[1];
  const data = await fetchTMDB(`/3/movie/${movieId}`, { ... });
```

The `movieId` value is interpolated into a URL without length validation. A request to `/api/movie/AAAA...(10KB)...AAAA` passes the regex, generates a 10KB cache key (`cacheKey = pathname + url.search`), hits the cache Map (miss), then sends a request to TMDB with a 10KB path. The TMDB 404 response gets handled, but the cache key bloats memory and the log entry is oversized. Trivially prevented with an ID length check (TMDB IDs are at most 8 digits).

## Input validation asymmetry across deployment targets

The Bun server validates:
- `page` must be integer 1-1000, returns 400 otherwise
- Search `query` must be non-empty and ≤200 chars after trim, returns 400 otherwise

Neither `middleware.js` (Vercel) nor `functions/api/[[path]].js` (Cloudflare Pages) implements these checks. Both pass `page` and `query` directly to `fetchTMDB`. TMDB itself caps page at 500 and returns an error for page > 500, but that error surfaces as a 502 "Bad Gateway" rather than the descriptive 400 the Bun server returns.

## Cache eviction cost at capacity

The original FIFO eviction deleted a single entry (O(1)). The replacement sorts all 10,000 entries by `createdAt` then deletes 10% (1,000 entries). The sort is O(n log n) and runs on every insertion while at capacity. Given the server processes requests sequentially in Bun's single-thread model, this adds latency to requests that arrive when the cache is full. A `Map` already preserves insertion order in JS — deleting from the front achieves FIFO in O(1). An LRU strategy would require touching entries on read, but even that is cheaper than a full sort.
