# VidAPI embed URL compliance, player skinning, and content filtering

This change fixes the embed URL query parameter from `?t=` to `?resumeAt=` across web and mobile surfaces to comply with VidAPI documentation, adds a `skin=netflix` parameter and `ds_lang` subtitle-language parameter to all player embed URLs, introduces a topbar EN/ID language selector on both surfaces, and applies a three-layer invalid-item filtering strategy (server, API client, render component). The implementation is symmetrical across web and mobile with appropriate platform differences (localStorage vs AsyncStorage, URLSearchParams vs manual string building).

**Watch for:** The web `getDsLang()` is called at render time rather than reactively, so changing the language preference does not update an already-rendered player page until navigation or remount (confirmed). The mobile `ContentGrid` filter checks for `item.id || item.tmdb_id` while the mobile `api.js` filter checks for `item.id && item.title` — different predicate shapes across the same data path (confirmed). The transform.test.js filtering tests define their own local `filterValidItems` function rather than importing the real one, so they don't actually test the production code path (confirmed).

## High-level view

The embed URL construction was refactored from simple string concatenation with `?t=` into a parameterized builder that emits `?resumeAt=...&skin=...&ds_lang=...`. The web version uses `URLSearchParams` for encoding safety; the mobile version uses manual array joining to sidestep an ESLint globals issue with Expo's config. Both approaches produce correct output for the current parameter set, but the mobile path would need manual encoding if parameter values ever contain special characters.

Language preference is stored in localStorage (web) / AsyncStorage (mobile) and surfaced as `ds_lang` in the embed URL. Neither surface broadcasts language changes to already-mounted components — the embed URL is only rebuilt on mount or navigation.

Content filtering applies at three levels: server routes strip items missing `id` or `title` after TMDB transform, the `fetchWithCache` layer in both surfaces re-filters, and the `ContentGrid` component skips rendering items without an identifier. The server and API layers use strict AND logic (`id && title`), but the ContentGrid components use lenient OR logic (`id || tmdb_id`), which means an item with only `tmdb_id` and no `title` would pass ContentGrid but be stripped by the API layer above it — the safety net is more permissive than the filter it backs up.

## Embed URL parameter refactor

The web implementation uses `URLSearchParams` which handles encoding correctly:

```js
const params = new URLSearchParams();
if (resumeAt) params.set('resumeAt', String(Math.floor(resumeAt)));
if (options.skin) params.set('skin', options.skin);
if (options.dsLang) params.set('ds_lang', options.dsLang);
```

The mobile implementation uses manual array building:

```js
const parts = [];
if (resumeAt) parts.push(`resumeAt=${Math.floor(resumeAt)}`);
if (options.skin) parts.push(`skin=${options.skin}`);
if (options.dsLang) parts.push(`ds_lang=${options.dsLang}`);
```

The divergence exists because Expo's ESLint config doesn't expose `URLSearchParams` as a global. The parameter values are constrained to known-safe strings ('netflix', 'id', numeric timestamps) today, but this creates a maintenance asymmetry. If a future skin name or language code contains reserved URL characters, the mobile path will produce malformed URLs while the web path auto-encodes.

## Language preference and `ds_lang` propagation

The web `getDsLang()` is called inline during render in both detail pages:

```js
const embedUrl = getMovieEmbedUrl(playId, resumeAt, { skin: 'netflix', dsLang: getDsLang() });
```

This happens at component body level, not inside a click handler or effect. Changing language from the topbar does not trigger a re-render of the detail page — `lang` state lives in `Layout.jsx` and doesn't propagate down via context or props. The user must navigate away and return for the new language to take effect on the player URL.

On mobile, `getDsLang()` is async and called inside the `buildUrl` effect. The dependency array is `[type, id, season, episode, contentId]` — language is not a dependency. Same staleness issue: a language change mid-session won't update the current player until navigation forces a remount.

## Three-layer content filtering

The server filter is consistent across all 12+ route handlers: `.filter(item => item.id && item.title)`. The web API layer applies the same predicate. But the ContentGrid components (both web and mobile) use a different check: `item && (item.id || item.tmdb_id)`. This OR logic is more permissive — it lets through items that have `tmdb_id` but no `id`, and items that have `id` but no `title`.

The web `ContentGrid` check doesn't validate `title`, meaning a titleless item that somehow bypasses the API filter would render as a card with empty text. The mobile `ContentGrid` has the same `item.id || item.tmdb_id` check. An item with `tmdb_id` but no `id` would render in the grid but break on navigation, since routes consume `item.id` for URL construction.

## Test coverage gap in transform.test.js

The `player.test.js` tests import and test the real production functions — solid coverage.

The `transform.test.js` additions define a local `filterValidItems` function:

```js
describe('TMDB Response Transform - Item Filtering', () => {
  function filterValidItems(items) { /* inline copy */ }
  ...
});
```

This validates the algorithm but not the deployment. If `api.js`'s `filterValidItems` is modified (say, adding `poster_url` as required), these tests continue to pass. The fix: export `filterValidItems` from `api.js` and import it in the test, or extract to a shared utility module.
