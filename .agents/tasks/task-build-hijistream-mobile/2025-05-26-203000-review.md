# Expo React Native mobile/TV app for HIJISTREAM

The change adds a complete Android TV/Google TV app at `/apps/mobile/` using Expo SDK 52, Expo Router, React Native WebView, TanStack Query, and Zustand. The utilities (api, cache, player, storage) are ported from the web app with synchronous-to-async conversion for AsyncStorage. The UI follows the web's dark theme and adds TV focus management via a `TVFocusable` wrapper component. A secondary change adds ESLint, TypeScript type-checking, and `jsconfig.json` to the existing web app.

**Watch for:** The `staleTime: 0` in QueryClient means double-layer caching (TanStack + AsyncStorage) will always re-run the AsyncStorage cache lookup on every render (confirmed). `ContentGrid` computes column count once at mount via `Dimensions.get` and never reacts to window resize, which matters for TV displays connected to varying resolutions (confirmed). The WebView player cannot communicate progress back unless the embedded player posts messages to `ReactNativeWebView.postMessage`; no injection script bridges this gap (confirmed). Zustand is listed as a dependency but never used anywhere in the mobile app (confirmed).

## High-level view

The mobile app is a faithful structural port of the web version. Screens map one-to-one (home, movies, tv, search, movie detail, tv detail, player). Data flows through the same API endpoints and cache TTLs. The main architectural choice was to keep the utility layer identical in behavior, converting localStorage's synchronous API to AsyncStorage's async one. This preserves API parity but introduces subtle timing concerns — the cache lookup in `fetchWithCache` is async, so TanStack Query's own stale/cache layer and the AsyncStorage cache are two independent caches with potentially conflicting lifetimes.

TV focus handling is centralized in `TVFocusable`, which wraps `TouchableOpacity` with `onFocus`/`onBlur` state, a 3px blue border, and `tvParallaxProperties`. This is the correct pattern for React Native TV, though it relies on the deprecated `tvParallaxProperties` prop that was removed from the community fork of React Native for TV — whether it works depends on which RN TV package the Expo build resolves to.

The WebView-based player loads the VidAPI embed URL and listens for `onMessage` events. The critical gap is that the embedded web page must call `window.ReactNativeWebView.postMessage(...)` for the RN side to receive anything. No injected JavaScript bridges this, so progress tracking will silently fail unless the embed player already uses that API (which is not guaranteed from a third-party service).

The web app changes are minor lint/type-check scaffolding and variable renames to suppress unused-variable warnings. They don't change behavior.

## Dual-cache architecture and staleTime conflict

The mobile app runs two independent caching layers: TanStack Query (in-memory, lifecycle tied to the QueryClient) and the AsyncStorage cache in `utils/cache.js` (persistent, TTL-based). The QueryClient is configured with `staleTime: 0`:

```javascript
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 0,
      retry: 1,
      refetchOnWindowFocus: false,
    },
  },
});
```

With `staleTime: 0`, every component mount triggers a refetch. But `fetchWithCache` checks AsyncStorage first and returns cached data without a network request if the TTL hasn't expired. The result: TanStack Query thinks data is "fresh from a fetch" but it's actually stale AsyncStorage data. The user never sees truly fresh data until the AsyncStorage TTL expires, yet the app performs an async disk read on every mount — the worst of both worlds.

The web app has the same structural issue, but there the localStorage reads are synchronous and essentially free. On mobile, each cache check is an async operation that introduces latency without providing stale-while-revalidate benefits.

## WebView player communication gap

`VideoPlayer.jsx` parses `event.nativeEvent.data` looking for `PLAYER_EVENT` messages:

```javascript
const handleMessage = useCallback((event) => {
  try {
    const data = JSON.parse(event.nativeEvent.data);
    if (data.type === 'PLAYER_EVENT' && data.data) { ... }
  } catch { }
}, [contentId, metadata]);
```

The `onMessage` callback on React Native WebView only fires when the embedded page calls `window.ReactNativeWebView.postMessage(...)`. The VidAPI embed player likely uses `window.postMessage(...)` (the standard web API), which targets the parent iframe, not the React Native bridge. Without an `injectedJavaScript` prop that patches `window.postMessage` to forward to `ReactNativeWebView.postMessage`, progress tracking will never fire. This means:

- Watch progress is never saved
- "Continue Watching" on the home screen will always be empty
- The resume-at feature will never have data to resume from

This is the single most impactful functional gap in the implementation.

## Static grid columns and TV display adaptation

```javascript
function getNumColumns() {
  const { width } = Dimensions.get('window');
  if (width < 1280) return 4;
  if (width < 1920) return 5;
  return 6;
}
```

This function is called once during render. On Android TV, the app launches at whatever the display's native resolution is and typically doesn't change. However, if a user connects to a different display or if the app window resizes (multi-window on newer Android TV devices), the column count is stale. The `key={grid-${numColumns}}` prop on FlatList is a good pattern for forcing re-render on column change, but the value never changes after mount.

## FlatList-in-ScrollView anti-pattern on home screen

The home screen wraps three horizontal `FlatList` components inside a `ScrollView`:

```jsx
<ScrollView style={styles.container} contentContainerStyle={styles.content}>
  <FlatList data={watchProgress} horizontal ... />
  <FlatList data={movies} horizontal ... />
  <FlatList data={tvShows} horizontal ... />
</ScrollView>
```

React Native explicitly warns against nesting VirtualizedLists inside plain ScrollViews because it disables virtualization for the inner lists. For horizontal lists with limited items (8 max here), the performance impact is minimal, but the console warning is noisy and signals potential issues on lower-end TV hardware with larger datasets.

## Missing functionality relative to TDD

The TDD specifies several items that are absent:

- **Zustand stores** (`contentStore`, `playerStore`) — not implemented. State management relies entirely on TanStack Query and local component state.
- **Player event handling for `completed` and `seeked` status** — the `VideoPlayer` only saves progress on `playing`/`paused`; it doesn't handle completion (which per the TDD should trigger "show next episode" for TV shows).
- **Focus memory** — the TDD specifies storing the last focused item per screen and restoring on navigation return. No such logic exists.
- **`injectedJavaScript` for postMessage bridging** — needed per the TDD's "Mobile: WebView with onMessage handler" specification, which implies the bridge is in place.

## Web app changes

The web app diff adds ESLint (flat config, React plugin), a `jsconfig.json` for TypeScript-powered type checking, and renames unused variables to `_`-prefixed names (`progress` to `_progress`, `type` to `_type`, `tmdbId` to `_tmdbId`). The `EpisodeList.jsx` change adds `/** @type {any} */` casts to suppress type-checker warnings about the `seasons` parameter union type. These are non-behavioral cleanups that prepare the web app for CI lint/typecheck gates.
