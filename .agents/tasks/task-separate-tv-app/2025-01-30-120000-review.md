# Monorepo split: dedicated TV app with shared package extraction

This change refactors a single mobile app (that tried to serve both phone and TV) into a proper monorepo with three concerns separated: a `packages/shared/` library for utilities, i18n, and theme; a `apps/tv/` standalone Android TV app built on react-native-tvos; and a simplified `apps/mobile/` that drops all TV-related code and reverts to standard react-native. The TV app gets its own native overlay video player with D-pad-navigable subtitle and settings modals, a top navigation bar replacing bottom tabs, and a hero carousel with auto-slide. A GitHub Actions CI workflow builds TV APKs per ABI.

Watch for: the TV player's seek and play/pause controls rely on postMessage to an iframe whose origin isn't controlled by this app, meaning those commands may silently fail depending on the embed player's CSP and message listener implementation (**likely**); subtitle selection rebuilds the entire embed URL and reloads the WebView, losing player position (**confirmed**); the domain allowlist in `onShouldStartLoadWithRequest` will block any CDN the embed player adds in the future, causing silent video failures (**likely**).

## High-level view

The shared package extracts API, caching, storage, player, i18n (7 locales), theme, and hooks into `packages/shared/` with a barrel `index.js`. Both apps consume it as a workspace dependency via deep imports (`@hijistream/shared/utils/api`), but the package.json lacks an `exports` field, making the public API surface its entire directory structure.

The TV app is a full Expo Router application using `react-native-tvos`. Navigation is a custom top bar with `TVFocusable` components (Pressable + animated scale + focus ring). The hero carousel auto-advances every 8 seconds and pauses on focus. Content rails are horizontal FlatLists with focus-scale cards.

The TV video player is a WebView loading the vaplayer.ru embed, overlaid with native React Native controls that appear on D-pad interaction and auto-hide after 6 seconds. Subtitle selection changes `dsLang` in the embed URL, which means a full WebView reload and loss of playback position. Playback speed is injected via postMessage without reload. Play/pause and seek also use postMessage with synthesized keyboard events, relying on the embed player to have a compatible message listener.

The mobile app reverts to standard react-native, strips all TV conditionals, and simplifies the VideoPlayer to a pure WebView wrapper. Mobile users rely entirely on the embed player's built-in touch controls for CC and settings, while TV users get native overlay controls because the embed's touch-based UI isn't D-pad accessible.

The CI workflow builds arm64-v8a and x86_64 APKs via `expo prebuild` + Gradle, with a fragile `sed` patch for ExpoModulesCorePlugin compatibility and GitHub Actions version pins that may not exist yet.

<details>
<summary>Issues (7)</summary>

1. **Subtitle reload loses playback position** — `handleSubtitleSelect` calls `buildUrl` which sets a new `embedUrl`, triggering a full WebView reload. Save `progressRef.current.time` as `resumeAt` in the rebuilt URL so the player resumes from where it was.
2. **Cross-origin postMessage may be silently ignored** — play/pause and seek inject key-event messages into the vaplayer iframe via `postMessage`. If the iframe's content security policy doesn't listen for these messages or validates origin, the commands do nothing with no feedback to the user.
3. **Domain allowlist is brittle** — `onShouldStartLoadWithRequest` allowlists 7 domains. If vaplayer.ru starts loading streams from a new CDN, video silently fails. No logging or user feedback on blocked requests.
4. **Progress persistence depends on unverified postMessage contract** — the TV player saves progress based on `{ type: 'progress', time, duration }` messages from the iframe. If the embed player changes or doesn't emit these events, progress tracking silently stops.
5. **No error state in TV player** — if the WebView fails to load (network error, blocked domain), the user sees a black screen with no feedback or retry option.
6. **HeroBanner auto-slide timer leak on fast navigation** — `startAutoSlide` is called in `useEffect` depending on `isPaused`, but if the component unmounts during the `pauseTimeoutRef` callback, `startAutoSlide` fires on an unmounted component. The cleanup clears both refs, but there's a race window between `pauseTimeoutRef` firing and the cleanup running.
7. **Shared package has no `exports` field** — consumers use deep imports like `@hijistream/shared/utils/api` which work because Node resolves into the package directory, but if the package ever gets published or the resolver changes, these deep paths may break without an explicit `exports` map in package.json.

## TV VideoPlayer: overlay architecture and the iframe control gap

The overlay auto-hides after 6 seconds and reappears when the user presses a hidden fullscreen `Pressable` trigger that captures the D-pad "select" event. Control commands are forwarded to the iframe via `postMessage` using synthesized keyboard events:

```javascript
iframe.contentWindow.postMessage(JSON.stringify({
  type: 'keydown', key: ' ', keyCode: 32
}), '*');
```

This relies on the vaplayer embed's inner player listening for `message` events and interpreting them as keyboard input. Cross-origin iframe restrictions mean `postMessage` is the only viable channel. If the embed player doesn't have a corresponding message handler that processes these synthetic key events, the buttons do nothing. The play/pause state is toggled optimistically (`setIsPlaying(!isPlaying)`) without confirmation from the player, so the UI can desync from actual playback state.

The subtitle selection path is the sharper problem. `handleSubtitleSelect` calls `buildUrl(code)` which constructs a new URL with the `dsLang` query parameter and calls `setEmbedUrl(url)`. This causes the WebView to load a completely new page, destroying all player state:

```
User selects subtitle -> buildUrl('fr') -> setEmbedUrl(new URL) -> WebView reloads -> player starts from 0:00
```

The `resumeAt` prop is only passed once from the parent route and isn't updated during playback. The progress ref tracks time locally but never feeds it back into the URL on subtitle change. The fix is straightforward: include `progressRef.current.time` as the `resumeAt` parameter when rebuilding the URL.

## Domain allowlist asymmetry and brittleness

Mobile uses string prefix matching (`url.startsWith('https://vaplayer.ru')`) while TV uses URL parsing with domain suffix matching (`domain === d || domain.endsWith('.' + d)`). The TV version handles subdomains correctly; the mobile version would miss them. Both share the same 7-domain list but implement matching differently, which means a new domain added to one could be forgotten in the other.

The core risk: vaplayer.ru loads video streams through CDN URLs that rotate. If they add a new CDN, `onShouldStartLoadWithRequest` blocks it silently. The user sees the player UI load but video never starts, with no error indication. Consider adding an `onError` handler or logging blocked URLs to surface failures.

## CI workflow fragility

The `ExpoModulesCorePlugin` patch (`sed -i` replacing `from components.release`) is a workaround for Expo SDK 52 CI builds. If the target line changes in a future expo-modules-core update, the sed silently doesn't match and the build fails at Gradle time with an opaque error.

The `actions/checkout@v6`, `actions/upload-artifact@v7`, and `actions/download-artifact@v8` version pins are ahead of what's currently published (v4 is latest for checkout and artifact actions as of this writing). If these don't exist at build time, the workflow fails immediately on the first step.

## Test coverage

There are no tests in this diff. The CI workflow only builds; it doesn't run any test suite.

Not tested: focus navigation order across screens, overlay show/hide timing, progress save accuracy, subtitle URL rebuild logic, domain allowlist correctness, postMessage command delivery to the embed player.
